# Review — MR‑2 coordinator protocol (durable history, reset, fencing, crash atomicity)

## Summary

The crash‑boundary machinery around a single journaled operation is sound. I traced all four injected boundaries (`before_journal` / `after_journal` / `after_sql` / `after_ack` in `src/store/machine_allocation.rs:231-249`) against `reconcile_pending_machine_commit` for Arm, Ticket, Release, Acknowledge and Reconciled, and each converges to exactly one durable outcome with no lost start right and no freed vector. The registry‑before‑SQL ordering, the `owns()` allocation fencing, the connection‑epoch fencing at `machine_exchange`, the retained-`Armed`-on-Withdraw rule, and the manager‑side seal/outbox invariants are all correct as written.

The defects I found are concentrated in **convergence after the coordinator‑reset path**, and in **capacity of the durable substrate**:

- Two `manager::bind` predicates reject exactly the two states that the coordinator's own reset recovery deliberately produces (rotated `authority_epoch`; retired floor above the manager's applied watermark). Both are permanent dead ends with no implemented recovery operation.
- The reset‑independent registry is a single 4 MiB blob that must hold every potentially‑used Grant. That cap is smaller than the grant inventory the protocol document mandates, and overflow surfaces as an untyped I/O error that the outbox will retry forever.
- `GrantState::Uncertain` is read in six places and written in none; there is no audited clearance for an unresolvable attached Grant, so §7's "Guest reset or pairing history loss → inventory/clearance" has no terminal state.
- Cross‑domain **fences** cannot collide with native leases because the two paths compare different string namespaces (impacts are unaffected; scalars are correct).

Nothing I found lets a released vector be reused or a start right vanish — the failures are fail‑closed. But several are *permanently* closed with no protocol move that reopens them, which is what blocks MR‑2 closure.

## Findings

### F1 — [High] Registry byte cap is smaller than the mandated Grant inventory; overflow is an untyped error the outbox retries forever

**Where:** `src/authority.rs:15` (`MAX_REGISTRY_BYTES = 4 MiB`), `src/authority.rs:1117-1131` (`publish`), `src/authority.rs:342-383` (`prepare_machine_commit`), `src/authority.rs:282-286` (unreachable 65,536 check); bounds in `src/machine.rs:21-24`; protocol §5 ("65,536 unresolved grants per machine, 4,096 per domain").

**Trace:**
1. Managers arm N allocations. Each Arm/Ticket calls `prepare_machine_commit`, which does `next.machine_permissions.insert(grant.grant_id, grant.clone())` and then `publish`.
2. `publish` serializes the *entire* registry (holds + participants + all `machine_permissions` + `native_permissions` + `retired_allocations` + pending intent) and rejects at 4 MiB.
3. A `GrantSnapshot` carries `grant_id` (2 UUIDs), a full `Candidate` (5‑UUID `AllocationKey`, owner, claims, 64‑char config digest, optional observed/quiet policies) and its `tickets: Vec<InvocationIntent>` (each with 2 IDs, 2 64‑char digests, a challenge UUID and an optional `TicketCleanup`). Conservatively ≥700 B, realistically ≥1 KB serialized.
4. At ~4,000 live grants — *below* `MAX_DOMAIN_CANDIDATES = 4096` for a single domain — `publish` returns `Err("authority registry exceeds durable byte limit")`.
5. `machine_exchange` propagates that as an untyped error, the SQLite tx is dropped, and the operation is never recorded. `manager::pending` returns the same earliest unapplied row on every reconnect → the manager retries the identical Arm indefinitely.

**Invariant violated:** protocol §5 "Retain every live/uncertain grant/ticket/outbox operation without expiry. Maximum 65,536 unresolved grants per machine, 4,096 per domain; reaching a limit blocks new starts, never deletes obligations." The declared limits are unrepresentable, and the enforced limit is neither a typed `limit_exceeded` reply nor documented.

**Note (correction to a plausible reading):** the size check at line 1122 runs *before* `self.state = State::Unknown`, so this does **not** poison the authority — the failure mode is a permanent inability to arm, not a machine‑wide `authority_history_unknown`. That makes it quieter and harder to diagnose, not safer.

**Fix:** move `machine_permissions` / `native_permissions` out of the single blob into per‑domain, individually‑published permission files (each already atomically written and checksummed), keeping the small registry for identity/epoch/holds. Enforce the documented per‑domain and per‑machine grant counts at `Arm`/`AuthorizeInvocation` time as `Outcome::Rejected { code: "limit_exceeded" }` so the manager stops rather than spins.

**Test:** arm 4,096 fake‑manager allocations in one domain; assert all are journaled and recoverable across a kill, and that the 4,097th receives a typed `limit_exceeded` reply, not an I/O error. Negative control: a build that silently evicts a permission to fit the cap must fail the "retained after kill" assertion.

### F2 — [High] After the authority epoch rotates, no attached manager can ever rebind

**Where:** `src/authority.rs:599-601` (`complete_machine_reset` sets `next.epoch = Uuid::now_v7()`), `src/store/machine.rs:365-374` (session takes `snapshot.epoch`), `src/machine/manager.rs:81-93` (`bind` prior‑session check).

**Trace (minimal):**
1. Coordinator SQLite is reset; `machine recover` runs. `prepare_machine_reset_recovery` rebuilds under the *unchanged* epoch `E0`, so managers reconnect, reconcile and release every grant normally.
2. `finish_machine_reset_recovery` → `complete_machine_reset` publishes `epoch = E1` and sets every `anchor.session = None`.
3. The manager reconnects. `machine_connect_begin` builds `session.authority_epoch = E1`; `machine_connect_finish` succeeds (the coordinator side is fine).
4. The manager calls `bind`. `prior` is the stored `E0` session; `prior.authority_epoch != session.authority_epoch` → `History("authority change requires inventory reconciliation")`.
5. Nothing clears `attached_peer.session_json`: `initialize` uses `INSERT OR IGNORE`, and `manager.rs` exposes no reconciliation/reset entry point. The manager is unbindable forever, with zero outstanding obligations.

**Invariant violated:** protocol §5 "Ordinary reconnect/released-ack loss automatically converges"; R‑MR‑4's requirement that reconciliation watermarks and release outboxes *provide* recovery. The doc comment on `bind` names the required step ("the caller must first run full inventory recovery") but that step does not exist.

**Fix:** add an explicit epoch‑advance branch to `bind`: accept `session.authority_epoch > prior.authority_epoch` when every `attached_grants` row is sealed **and** acknowledged `Released`; otherwise transition `attached_peer` into a durable `history_unknown` state that *permits* the bind (so `ReconcileBegin/Page/Commit` can run) while refusing `consume_ticket` and new `enqueue` of `Arm`/`AuthorizeInvocation` until the reconcile commits.

**Test:** public fake‑manager round trip — pair, arm, release all, drive a full reset recovery to epoch rotation, assert the same manager rebinds and can arm again. Negative control: a manager holding one unreleased `Armed` grant must **not** silently rebind across the rotation; it must land in the reconciliation state and retain the grant.

### F3 — [High] Reset recovery retires responses the manager has not applied, and `bind` treats that as fatal

**Where:** `src/store/machine_reset.rs:71-87` (`accepted` computed, `retired_sequence_floor = accepted_sequence = accepted`, `retire_machine_sequences`), `src/machine/manager.rs:73-75` (`participant.retired_sequence_floor > applied` → error).

**Trace:**
1. Manager enqueues `AuthorizeInvocation` at sequence 5, sends. Coordinator commits, journals, checkpoints, replies. **The reply is lost.** Manager state: `applied = 4`, `next = 6`, `retired_floor = 0`. Coordinator/anchor: `accepted_sequence = 5`.
2. Coordinator SQLite is reset; `prepare_machine_reset_recovery` writes `machine_domains(..., retired_sequence_floor = 5, accepted_sequence = 5)` and calls `retire_machine_sequences(domain, 5)`. The `machine_operations` row for 5 is *not* retained (only a single `pending` intent is re‑inserted; this one had already been finished).
3. Manager reconnects; `ParticipantSnapshot { accepted_sequence: 5, retired_sequence_floor: 5 }`.
4. `bind`: `5 > 4` → `History("peer watermark/session differs from durable manager history")`. The manager cannot bind, cannot reconcile, cannot ever discover that ticket 5 was issued.

**Invariant violated:** protocol §10 "Lost response history receives an explicit retired floor… A request at/below the floor without a retained exact response returns `history_unknown`, never new work." The design says *reply* `history_unknown`; the implementation refuses the session, so the request is never asked. The coordinator retains the grant and ticket (accounting safe), but the obligation can now only be cleared by an operator, contradicting R‑MR‑4's "durable idempotent release outboxes provide recovery".

**Fix:** treat `retired_sequence_floor > applied` in `bind` as a *state*, not an error: bind, mark every outbox row with `sequence <= floor AND outcome_json IS NULL` as `history_unknown`, block `consume_ticket` for the affected allocations, and require a `ReconcileBegin/Page/Commit` round before any new `Arm`/`AuthorizeInvocation` for that domain. The coordinator's `ReconcileCommit` (`machine_allocation.rs:831-851`) already forces the manager's snapshot to cover every issued ticket, so the lost ticket is recovered there.

**Test:** kill the transport between coordinator commit and manager `accept` for an `AuthorizeInvocation`, then run reset recovery; assert the manager rebinds, that reconciliation surfaces the coordinator‑issued ticket the manager never saw, and that the grant is released only after a sealed proof covering it. Negative control: a manager that simply re‑advertises the candidate and arms afresh, ignoring the orphan ticket, must fail.

### F4 — [High, closure] `GrantState::Uncertain` is never assigned; there is no clearance path for an unresolvable attached Grant

**Where:** produced nowhere. Consumed at `src/store/machine_allocation.rs:196-198, 458-467, 564-565, 831`, `src/store/machine_queue.rs:18, 305`, `src/store/machine_reset.rs`, `src/store/machine.rs:171`, `src/store/machine_recovery.rs`.

**Trace:**
1. Manager's SQLite store is reset (new `store_uuid`). `machine_connect_begin` rejects: `participant.manager_store_uuid != hello.manager_store_uuid` → `history_unknown` (`src/store/machine.rs:341-348`). Correct.
2. The domain's `Armed` grants stay `Armed` forever, retaining the full vector via `remote_debits` (`machine_queue.rs:17-23`).
3. There is no coordinator operation that marks them `Uncertain`, and `force_release_authority` (`src/store/authority.rs:225-234`) operates on `AuthorityHold`s only — it cannot touch a Grant.
4. `finish_machine_reset_recovery` requires `NOT EXISTS(machine_grants WHERE state IN ('offered','armed','uncertain'))`, so a coordinator reset can never complete either.

**Invariant violated:** §4 "Grant state is `offered -> armed -> released`, with `uncertain` retaining armed accounting"; §5 "no proof means retained gate until audited operator clearance"; R‑MR‑4 "unresolved proof requires retained accounting **or explicit audited risk clearance**"; R‑MR‑6 requires exposing "reconciliation blockers". §7 negative controls M‑A05/M‑A07 depend on this state existing.

**Fix:** (a) transition `Armed → Uncertain` on the three conditions §5 names — snapshot omits an expected allocation, sequence gap, changed manager store — instead of only returning `Outcome::Rejected{"history_unknown"}` from `ReconcileCommit`; (b) add an owner‑authenticated `doctor clear-grant <grant-id> --force` that requires an explicit risk‑acceptance reason, records operator identity plus the exact affected tickets, retires the allocation key into `retired_allocations`, and is refused for a managed peer (mirroring `arm_bootstrap`'s peer/root check).

**Test:** reset a fake manager's store, assert the grant becomes `Uncertain` and still debits; assert the coordinator gate stays closed; assert audited clearance releases it and writes an audit file; negative control — a TTL/disconnect path that reaches `Released` without the audit record must fail.

### F5 — [High, closure; assumption‑dependent] No offer delivery path; a 5 s offer TTL against ≤10 s manager polling

**Where:** `src/machine.rs:25` (`OFFER_MILLIS = 5000`), `src/machine.rs:457-504` (`Command` has no `Offer` variant), `src/store/machine_queue.rs:483-501` (offers created coordinator‑side only), `src/store/machine_queue.rs:255-266` (expiry writes a 5 s `not_before_ms` backoff), protocol §3 (lists `Offer` as an operation) and §6 ("batch refresh at most once per 10 s while candidates exist"; "Idle connections use OS event waits without heartbeats").

**Trace:** manager upserts a candidate → coordinator creates an `Offered` grant in `machine_offer_before_native` → nothing notifies the manager → the manager's only discovery move is `Command::Inspect` → at the documented ≤10 s refresh cadence the 5 s offer is already `Expired` and the candidate has a fresh 5 s `not_before_ms`. Attached work never arms.

**Invariant violated:** §3's `Offer` operation row and §6's aging/queue contract; R‑MR‑3 "Windows and attached candidates MUST enter one priority/aging/reservation order with no domain head-of-line blocking". A-MR-2 (M‑A01..07) cannot be executed without this.

**Assumption:** the MR‑2 transport/reactor is not in the supplied file set. If it already pushes an unsolicited frame on offer creation, this is void — but `Reply` is strictly `{session, request_sequence, operation_id, coordinator_revision, outcome}` and `ProtocolRecord` (`machine.rs:155-166`) enumerates no server‑initiated allocation message, so I believe the gap is real.

**Fix:** either extend `Outcome::Accepted` on `CandidateUpsert` to carry an optional `GrantSnapshot`, or add a coordinator→manager `Offered` notification frame (versioned under `WIRE_VERSION`), or make `Inspect` a long‑poll bounded by `CANDIDATE_MILLIS` with an event wait. Whichever is chosen, `OFFER_MILLIS` must be ≥ the worst‑case discovery latency.

**Test:** W‑C1 style — one shared cargo slot, one native and one attached candidate; assert from the `machine_events` stream that the attached grant reaches `Armed` within one offer TTL. Negative control: a polling implementation that misses offers must show `Expired` events and fail.

### F6 — [Medium‑High] Cross‑domain fences can never conflict with a native lease (impacts and scalars are fine)

**Where:** `src/store/machine_queue.rs:39-67` (`physical_claims` renders every fence as `format!("domain:{}:{}", id.scope.0, id.resource_id)`), `src/store/machine_queue.rs:17-23` (`remote_debits` returns those `ResolvedClaims` for the native admission path), `src/store/machine_ticket.rs:160-210` (`authorize` mixes `native_debits` raw fences with `physical_claims_json` prefixed fences and calls `physical.blockers(...)`).

**Trace:**
1. An alias binds attached fence `scratch` to a shared filesystem object; `topology.expand` resolves it to a shared scope. `physical_claims` stores it as `domain:<scope-uuid>:<path>`.
2. A native Job's `leases.claims_json` stores the same object as its raw native fence identity.
3. Native admission compares its raw string against `remote_debits`'s `domain:`‑prefixed string → no match → both are admitted onto the same exclusive object.
4. `authorize`'s re‑check has the same blind spot in the opposite direction.

Note the asymmetry: `machine_offer_before_native` (lines 294-313, 396-408) does this correctly via typed `ScopedClaims` through `topology.expand`, so the *offer* is blocked while the *native admission* is not — the two paths disagree.

**Invariant violated:** R‑RES‑1 "One Lease grants the complete requested set atomically"; R‑MR‑3 "Fences are domain-local unless aliases explicitly bind a shared filesystem object"; §6 "No fence, impact or scalar is acquired partially." W‑C3's "parent has no fence overlapping scratch" control cannot detect the inverse violation.

**Scope note:** impacts *are* compared correctly (both sides carry unscoped names, so the `measurement` ⊥ `cpu_heavy` exclusion W‑C4 depends on works), and root‑scope scalars are correctly folded by `physical_claims`'s `key.scope == root` filter. Only fences are affected.

**Fix:** make the native admission path expand its lease claims through `ResourceTopology` (as `machine_offer_before_native` already does) and compare typed `ScopedClaims`, or canonicalize *both* sides into the same `domain:{scope}:{resource}` string form before any `ResolvedClaims::blockers` call.

**Test:** register an alias binding a native exclusive fence path to an attached domain fence; assert that a native Job and an attached Job claiming it cannot hold grants simultaneously, observed through complete `machine_events` grant transitions (not sampled state). Negative control: the current code must fail this test.

### F7 — [Medium‑High] An uncommitted pairing anchor gates the whole machine with no abandon path

**Where:** `src/authority.rs:615-657` (`prepare_pairing` rejects a different payload for the same `domain_id`), `src/authority.rs:903-906` (`authority_pairing_incomplete` blocks *all* admission), `src/store/machine.rs:191-216` (registry‑first ordering).

**Trace:**
1. Operator runs `machine pair`; `prepare_pairing` publishes an anchor with `committed: false`, carrying a freshly generated 32‑byte `PairingSecret`.
2. The process dies before `tx.commit()` / `commit_pairing`.
3. `admission_blocker` now returns `authority_pairing_incomplete` — native Windows Jobs are blocked too (correct per R‑MR‑4 "The gate also covers Windows work").
4. The operator retries. If the CLI regenerates the pairing secret (or the operator adjusts budgets/aliases), `prepare_pairing` returns `"domain already belongs to another pairing payload"`. `force_release` only handles `AuthorityHold`s. The machine is permanently blocked.

**Invariant violated:** §2 "Explicit first initialization requires an owner action… Reinitialization with lost history requires audited risk clearance, not an installation retry" — but a *never‑committed* anchor has no history to lose, so requiring clearance is disproportionate and no clearance operation exists anyway.

**Fix:** allow `prepare_pairing` to replace an anchor when `!committed` **and** it has no `session`, no `machine_permissions` referencing its `domain_id`, and no `machine_domains` row; or add an explicit `machine pair --abandon <domain-id>` guarded by the same conditions. Both are provably safe because an uncommitted anchor is filtered out of `machine_exchange` (`machine_allocation.rs:34-38`), `machine_connect_begin` and `machine_connect_finish`.

**Test:** kill between `prepare_pairing` and `commit_pairing`; assert the machine is gated; assert an exact replay commits; assert a differing‑payload replay is refused *and* that the documented abandon path clears it; negative control — abandoning a `committed` anchor, or one with a live grant, must be refused.

### F8 — [Medium] `retired_allocations` grows without bound inside the same 4 MiB blob

**Where:** `src/authority.rs:41-42` (`retired_allocations: BTreeSet<String>`), `src/authority.rs:396-401` (`finish_machine_commit` inserts one 64‑char hash per released allocation), never removed.

**Trace:** every attached allocation key retired adds ~70 serialized bytes permanently. Combined with F1's 4 MiB cap, ~55k released allocations exhaust the registry even with zero live grants — and, unlike grants, this set never shrinks. The check it protects (`prepare_machine_commit` refusing new start rights for a retired key) is genuinely required, since a manager could replay an old key.

**Invariant violated:** §5 "Completed per-operation rows may be compacted only after bilateral acknowledgement through a contiguous sequence watermark. Keep durable retired sequence floors, retired store epochs and domain anchors." The retained set is meant to be bounded *identity anchors*, not one entry per Lease.

**Fix:** replace the per‑key hash set with a per‑`(domain_id, manager_store_uuid)` monotonic retired watermark plus a small bounded recent‑key window, and reject any allocation key whose `lease_id` sorts below the watermark. `AllocationKey` already carries `manager_store_uuid` and `lease_id`, and `Uuid::now_v7` leases are time‑ordered, so a watermark is sufficient.

**Test:** release 100k allocations across a restart; assert registry bytes stay bounded, that replaying an ancient released key is still refused, and that arming continues to work.

### F9 — [Medium] `ReconcileCommit` journals every released Grant in one intent

**Where:** `src/store/machine_allocation.rs:219-224` (`Outcome::Reconciled { released, .. } => released.iter().map(load_grant)`), `src/store/machine_allocation.rs:852-888`, bounds at `machine.rs:24` + `machine_allocation.rs:738` (`page_count > 16` × `MAX_RECONCILE_PAGE = 256` → up to 4,096 allocations per snapshot).

**Trace:** a manager reconciles after a long outage with 3,000 sealed releases in one snapshot → `ReconcileCommit` builds `intent.grants` with 3,000 `GrantSnapshot`s → `prepare_machine_commit` → `publish` exceeds 4 MiB → the whole reconciliation fails with an I/O error and cannot be retried in smaller pieces (`ReconcileBegin` requires `begin_sequence == 0` and `end_sequence == accepted`, so the snapshot cannot be chunked).

**Invariant violated:** §5 "Reset requires inventory reconciliation of every registered potentially-used grant" — the only implemented path to complete it can be too large to journal.

**Fix:** journal `Reconciled` releases incrementally (one `prepare/finish` pair per page, or an intent that references grant IDs rather than embedding full snapshots, since the snapshots are already in `machine_permissions`), and bound `intent.grants` explicitly with a typed `limit_exceeded` rejection.

**Test:** reconcile 4,096 sealed allocations in one snapshot and assert the commit succeeds and survives a kill at each boundary.

### F10 — [Medium] `machine_connect_finish` publishes the new session before the SQL epoch update and rolls back only SQL on failure

**Where:** `src/store/machine.rs:422-433`.

**Trace:** `accept_machine_session(challenge.session)` publishes the registry anchor at epoch `E`. The next statement updates `machine_domains … WHERE connection_epoch < E AND manager_store_uuid = ?`. If `changed != 1`, the function returns `Err` and the SQLite transaction is dropped/rolled back — but the registry already carries session `E`. Now `machine_exchange` rejects the new session (`participant.connection_epoch != request.session.connection_epoch`) *and* the old one (`anchor.session != request.session`): the domain accepts nothing.

**Severity qualification:** I could not construct a reachable trigger for `changed != 1` (a second `ConnectBegin` replaces the single `machine_challenges` row, so the stale finish fails the JSON comparison first, and `manager_store_uuid` is never mutated). The identical divergence is, however, reachable by a crash between `accept_machine_session` and `tx.commit()`. Both recover on the next `ConnectBegin`, because `reserve_machine_connection` takes `max(next_connection_epoch, sql_epoch) + 1`. So this is a transient‑unavailability defect, not a fencing hole.

**Fix:** commit the SQLite epoch update first *within* the tx, then publish the anchor session, then `tx.commit()` — or, keeping registry‑first ordering, perform the `changed != 1` check against the same values before publishing.

**Test:** inject a crash between `accept_machine_session` and `tx.commit()`; assert the manager's next `Connect` succeeds and that no operation signed under the abandoned epoch is ever accepted.

### F11 — [Low‑Medium] `Registry::load` validates holds/participants/coordinator but not the machine permissions or the pending commit

**Where:** `src/authority.rs:766-841` (`load`, exhaustive checks for `holds`, `participants`, `coordinator`, `domains`; none for `machine_permissions`, `native_permissions`, `retired_allocations`, `pending_machine_commit`); `src/store/machine_recovery.rs:37-52` applies `intent` without calling `intent.request.validate()`.

**Impact:** `reconcile_pending_machine_commit` inserts a `machine_operations` row, advances `accepted_sequence`, and calls `save_grant` for `intent.grants` on the strength of the journal alone. A structurally invalid intent (nil session UUIDs, a `grant.candidate.key` not owned by `request.session`, a `grant_id.store_uuid()` from a foreign store) would be applied. The envelope SHA‑256 and the atomic `MOVEFILE_WRITE_THROUGH` publication make this unreachable by corruption, and same‑owner tampering is outside R‑SCOPE‑2 — so this is a defence‑in‑depth and validation‑posture inconsistency rather than an exploitable hole.

**Fix:** extend `load`'s validation block with: map key equals `grant.grant_id` / `permission.invocation_id`; `payload_hash(&grant.candidate.key)` present in `retired_allocations` implies no live permission; and `pending_machine_commit.request.validate()` plus `request.session.owns(&grant.candidate.key)` for every grant.

**Test:** hand‑construct a checksum‑valid registry with a pending intent whose grant belongs to another store; assert `open()` yields `authority_history_unknown` rather than applying it.

### F12 — [Low] Two secondary observations

**(a) Full registry write + fsync inside the open IMMEDIATE coordinator transaction.** `src/store/machine_allocation.rs:229-254`: `prepare_machine_commit` → `publish` → `atomic_write` (create/write/`sync_all`/`MoveFileExW(WRITE_THROUGH)`) executes while the SQLite write lock is held, and a journaled operation performs up to three full‑file rewrites (`prepare`, `finish`, `checkpoint_machine_sequence`). Every native lifecycle transaction serializes behind these. This will show up in W‑C1's two‑cargo‑slot overlap measurement and in the MR‑3 idle/wake budget (§9). Recommend measuring it explicitly before MR‑3 and, if it binds, moving the permission journal to per‑domain files so the fsync payload is O(one grant).

**(b) `machine_events` is poisoned by an unexpected lease state.** `src/store/machine_events.rs:155-163`: `Record::Native`'s state match returns `StoreError::InvalidState` for anything other than `granted`/`released`, and the trigger (`machine_events.rs:23-29`) fires on *every* `leases` insert and state change. One row in another state makes the whole public event page fail until it ages out of the 4,096‑event window. R‑OBS‑3/R‑MR‑6 want an explicit Gap or `unavailable`, not a hard error. Recommend skipping or emitting an explicit `unavailable` marker for unrecognized states.

**(c) Ticket freshness binds the host sample, not the manager's challenge.** `src/store/machine_ticket.rs:144-152` bounds only `monotonic - sample.captured_monotonic_millis <= 250`. §4 requires the bound to be measured "from the manager's challenge send" and requires "Host sample must be taken after receipt of that challenge". `intent.readiness_challenge` is a bare UUID with no timestamp, and `manager::consume_ticket` (`manager.rs:344-365`) performs no freshness check at all — its doc comment defers this to an unimplemented runtime. This is an MR‑2 completion item, not a defect in shipped code, but W‑C4's "deliberately stale host evidence must cause the validator to fail" control cannot pass without it.

## Evidence Gaps

I could not verify the following from the supplied files; each would change my assessment if it contradicts my assumptions.

1. **Native admission and release call sites.** `check_authority_release`, `record_native_start`, `record_suspended_root`, `mark_started_with_identity` and the native blocker computation are not supplied. I assumed (i) native admission consults `authority_blocker()` and `machine_queue::remote_debits`, and (ii) the brief's statement that both native paths publish the permission before `ResumeThread`. F6 depends on assumption (i) for its native‑side direction; the `authorize` side is verifiable from the supplied code regardless.
2. **`crate::admission`** (`ResourceTopology`, `ScopedClaims`, `expand`, `machine_capacities`, `scalar_claim_entries`, `reservation_decision`). I assumed `expanded.impacts` are unscoped strings (which is why impacts cross‑match while fences do not) and that alias resolution rewrites a fence's `scope`. Both are inferable from `physical_claims`'s shape but not proven.
3. **The MR‑2 transport/reactor.** How `Request` frames reach `machine_exchange`, whether `machine_connect_begin` is peer‑authenticated *before* it burns a connection epoch and overwrites the pending challenge, and whether offers are pushed. F5 is contingent on this.
4. **`crate::host_observation`** (`HostSample`, `evaluate_request`, `quiet_budget`, `quiet_stability`, `observation_clock`). §4's mandatory rejection of "suspend/clock/provider generation discontinuities" and M‑A11's stale‑quiet control cannot be checked.
5. **`src/machine/manager/tests.rs`** is referenced at `manager.rs:453` but not supplied, so I cannot tell which of F2/F3 are already covered by a `#[should_panic]`‑style negative assertion versus untested.
6. **Fault‑injection build configuration.** `crash_boundary` is `#[cfg(debug_assertions)]` (`machine_allocation.rs:270`), so the 15 isolated fault tests exercise a debug profile only. The native `check`/`test`/MSRV gates therefore do not cover the injected recovery paths in the configuration that ships. Worth stating explicitly in the MR‑2 evidence ledger.
7. **`doctor` / `machine recover` surfaces.** R‑MR‑6's requirement to expose Grant/Lease associations, reconciliation blockers and concrete clearance actions is unverifiable here; F4's missing clearance operation is partly a doctor‑surface gap.

## Recommendations

**Must close before MR‑2 can be called done (in order):**

1. **F1** — re‑home the machine permission journal so the durable substrate can actually hold the mandated inventory, and convert overflow into a typed `limit_exceeded` reply. Everything else that writes the registry inherits this ceiling.
2. **F2 + F3** — make `manager::bind` model the two post‑reset states instead of refusing them, and add the reconciliation transition the doc comment already promises. These two are the difference between "reset recovery works" and "reset recovery is a one‑way door".
3. **F4** — implement the `Uncertain` transition and an audited Grant clearance. Without it §7's guest‑reset and epoch‑overlap rows have no terminal state and A‑MR‑2's M‑A05/M‑A06/M‑A07 cannot be executed.
4. **F5** — settle offer delivery (or prove the reactor already handles it) before writing any M‑A01..07 harness; the current TTL/poll relationship makes the happy path unreachable.
5. **F6** — unify the fence namespace across the native and attached admission paths.

**Should close before the public fake‑manager slice:** F7 (abandon path), F9 (chunk the reconcile journal), F8 (bounded retired watermark).

**Sequencing note:** F2, F3 and F4 are all discovered by the *same* harness — a public fake manager driven through pair → arm → ticket → lost reply → coordinator reset → recover → epoch rotation → rebind. Building that harness first will surface them together and is a better use of the next slice than fixing them one at a time.

**One protocol‑document amendment to consider:** §5's grant limits (65,536/machine, 4,096/domain) and §8's 4 MiB registry cap were written for different mechanisms and are mutually inconsistent. Whichever way F1 is resolved, one of the two numbers should be changed in `machine-resource-protocol.md` with an explicit derivation, so the ledger records a checkable bound rather than two aspirational ones.
