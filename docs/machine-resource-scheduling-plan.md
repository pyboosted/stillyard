# План: общий планировщик ресурсов машины и подключаемые среды выполнения

Дата: 2026-09-09. Статус: фазированный план и автономный handoff исполнителю;
целевой результат и порядок фаз согласованы, реализация фаз не начата.
Исходная ревизия: `5c440f6` (`0.1.0-alpha.14`).

## Вход для исполнителя без контекста переписки

Этот документ вместе с репозиторием содержит необходимый контекст задачи.
Переписка, прежние agent sessions, состояние goal и временные файлы внешних
ревью не являются входными зависимостями реализации.

**Первое действие:** прочитать [AGENTS.md](../AGENTS.md),
[CONTRIBUTING.md](../CONTRIBUTING.md), этот план и указанные в нём действующие
requirements. Затем выполнить MR-0 и последовательно MR-1..MR-3. Ближайшая
пользовательская поставка — завершённая MR-3 на текущей Windows/WSL-машине.
MR-4/MR-5 задают последующие поставки; отсутствие native Linux/Mac-стенда
не является поводом остановить работу над MR-0..MR-3.

**Порядок работы с контрактом:** этот план описывает согласованное расширение
существующего продукта. Его отличия от нынешних Windows-only/single-store
requirements намеренны и перечислены в MR-0. Исполнитель оформляет amendment
и acceptance для этих отличий до соответствующей реализации. Непересмотренные
гарантии действующих requirements сохраняются. План не отменяет build invariant
AGENTS.md и не разрешает молча ослабить containment или сохранность истории.

**Что уже решено:** один машинный координатор, местное владение заданиями,
динамические общие ресурсы Windows/WSL, поддержка standalone тем же ядром,
будущие вложенные execution domains и отдельная большая WSL-приёмка с живыми
потребителями. Не требуется заново выбирать между этим направлением,
двумя независимыми счётчиками и постоянными статическими квотами.

**Что ещё предстоит спроектировать:** wire/storage-форматы, точный протокол
release/recovery, resource mappings, bootstrap и способы доказательства WSL
cleanup. Это явная работа MR-0, а не подразумеваемые решения из переписки.
Критерии её завершения перечислены ниже. Называть план уже проверенной
распределённой state machine нельзя.

Рутинные инженерные решения в этих границах исполнитель принимает и фиксирует
сам. Основание для обращения к пользователю — необходимое изменение целевого
контракта, недоступные права/стенд/потребитель, либо воздействие на чужую работу
и данные. Сам переход к следующей закрытой по критериям фазе не требует
повторного выбора архитектуры. Разрешение на реализацию не означает разрешения
публиковать изменения или сбрасывать рабочие очереди с чужими заданиями.

## Результат и порядок поставки

Stillyard должен согласовывать тяжёлую работу на одной машине независимо от того,
выполняется она на хосте, в WSL или в dev-контейнере. Первым полноценным результатом
будет текущая Windows/WSL2-машина с одним общим планировщиком ресурсов и живыми
потребителями. Автономный Linux использует тот же код с местным координатором.

На каждой удалённой машине действует её собственный координатор. Выбор машины,
создание контейнеров и worktree, распределение агентов и управление SSH остаются
за внешними потребителями. План не добавляет межмашинные транзакции или размещение.

| Фаза | Поставка | Зависимость | Условие завершения |
|---|---|---|---|
| MR-0 | Контракт, схема отказов и рабочий путь bootstrap | — | Закрыты решения протокола и получены допустимые исходные Job-результаты |
| MR-1 | Общее ядро допуска и границы платформенного кода | MR-0 | Windows использует новое ядро без потери существующего поведения |
| MR-2 | Протокол координатора и подключённой среды | MR-1 | Проверены конкуренция, повтор сообщений, сбои и потеря истории |
| MR-3 | **WSL2 + Windows: общий планировщик, установка и живые потребители** | MR-2 | Выполнена вся матрица WSL и потребительская приёмка |
| MR-4 | Standalone Linux и несколько dev-контейнеров на Linux/WSL | MR-3 | Контейнеры динамически делят ресурсы своего реального хоста |
| MR-5 | macOS-координатор и Linux dev-контейнеры | MR-4 | Тот же протокол и потребительская матрица работают на Mac |

Статические квоты допустимы как явно обозначенная временная конфигурация разработки.
Они не закрывают MR-3 или сценарий динамического разделения ресурсов контейнерами.
Поддержка macOS и контейнеров не является предварительным условием поставки WSL.

## Архитектурные решения для всех фаз

1. **Один авторитет выдачи ресурсов на машину для подключённых участников.**
   Windows-задания и WSL-заявки проходят один алгоритм допуска, приоритетов и
   резервирования. Позднее к нему подключаются контейнеры. Несколько независимых
   per-user демонов не объявляются общим машинным координатором: первая поставка
   обслуживает одного владельца и явно привязанные среды. Общая политика нескольких
   независимых пользователей требует отдельного расширения доверия.
2. **Ресурсная топология явная.** Координатор знает машину, VM и среды выполнения,
   их отношения и лимиты. WSL-дистрибутив и контейнер не объявляют себе физическую
   ёмкость. Вложенность не выводится из местоположения Docker CLI или имени endpoint.
3. **Полный вектор плановых ограничений выдаётся в одной БД координатора.**
   В него входят машинные и доменные бюджеты, логические токены, совместимость
   impacts и зарегистрированные исключения. Нет последовательного захвата
   независимых дефицитных Lease у контейнера, WSL и хоста. Исполнитель дополнительно
   проверяет актуальную местную готовность и полномочия на запуск.
4. **Местный менеджер владеет жизненным циклом заданий.** Его SQLite остаётся
   источником истины для Submission/Job/Attempt/Invocation, логов и результатов.
   Он же управляет процессами и доказательствами очистки. В standalone менеджер,
   исполнитель и координатор размещаются в одном демоне.
5. **Машинный Grant соответствует местному Lease, а не TCP/pipe-сессии или PID.**
   Work Lease сохраняет Grant от primary через postconditions до безопасного
   освобождения. У probe отдельный Lease/Grant. Каждый запускаемый Invocation
   дополнительно связан со своим Containment и актуальным разрешением на release.
6. **Бюджеты, метрики и hard limits различаются.** CPU units и RAM claims —
   декларации для допуска; cgroup/VM limits — ограничения среды; наблюдаемая
   загрузка — evidence. Одна задача учитывается в ограничениях предков, но не
   считается несколькими физическими потребителями. Метрики Windows и WSL не
   складываются как независимые объёмы свободной памяти.
7. **У каждого ресурса есть область действия и идентичность.** Машинный
   `cargo_slots`, доменный бюджет и конкретный GPU различимы в API. Файловые
   fences по умолчанию доменные; общий каталог требует явной зарегистрированной
   идентичности/карты aliases. Одинаковый путь не доказывает общность файлов.
8. **Attached не переходит в standalone при обрыве связи.** Новые запуски требуют
   актуального разрешения; уже начавшаяся работа может продолжаться под местным
   контролем, а её Grant остаётся занят. Timeout соединения не доказывает очистку.
9. **Размещение и родство заданий остаются явными.** Batch, зависимости и managed
   parent/child находятся в одном местном store в первых поставках. Межсредовое
   родство нельзя имитировать переменными окружения. Агент не держит `cargo_slots`
   всё время чтения кода: отдельную сборку оформляет managed-заданием.
10. **Интеграция с runtime ограничена регистрацией, исполнением и наблюдением.**
    Stillyard не создаёт dev-окружения и не получает неограниченный доступ к Docker
    socket из каждого контейнера. Поддерживаемый адаптер обязан предоставить
    необходимое делегирование или ограниченную службу исполнения.

## MR-0. Контракт, исходная точка и bootstrap

**Цель:** убрать архитектурные неопределённости, которые заставили бы переделывать
Linux-runner или учёт ресурсов после появления первого рабочего WSL-бинарника.

### Работа

- Сопоставить текущий код с реально реализованными возможностями alpha.14.
  Исторические acceptance-таблицы не считать доказательством готовности всех
  перечисленных там функций. Базовые пробелы, например ещё не реализованные
  режимы остановки, отделить от регрессий и необходимого расширения этого плана.
- Подготовить amendment к [requirements.md](requirements.md): несколько execution
  domains одной машины, три роли демона, resource scopes, Grant, сброс store,
  аутентификация, WSL lifetime, публичные состояния и границы контейнерной поддержки.
  Затронуты R-PKG-1..6, R-SCOPE-1..4, R-DOM-1..4, R-STORE-1..6,
  R-RES-1..9, R-RUN-1..6, R-NEST-1..5, R-OBS-4 и R-LINUX-1..5.
- Зафиксировать совместимость JSON/protocol/SQLite. Отдельно описать, какие
  изменения схемы сбрасывают базы, и процедуру обновления двух установленных
  демонов без потери контроля над уже работающими задачами.
- Утвердить одну state machine протокола по разделу ниже: владелец каждого
  состояния, порядок durable writes, повторы, потерянные ответы, отмена,
  ограничение объёма истории, условия освобождения и восстановления.
- Зафиксировать правило общей очереди: координатор видит все заявленные готовые
  кандидаты, а не только один head каждой среды. Определить источник времени
  aging и tie-break, withdrawal при изменении готовности, резервирование полного
  вектора, конечные deferral/backoff и защиту от потока устаревших кандидатов.
- Назначить идентичности машины, VM, дистрибутива/контейнера, store, incarnation
  исполнителя и соединения. Для каждого события рестарта явно перечислить, чью
  очистку оно доказывает. Смена daemon generation или имени контейнера не является
  доказательством отсутствия процессов.
- Повторно обследовать текущую машину. Наблюдения 2026-09-07 — WSL2 x86_64,
  cgroup v2, user systemd, `Linger=no`, отказ Windows auto-start с access denied —
  являются исходными данными, а не результатами свежей приёмки.
- Восстановить работу установленного системного Windows-демона. Обновить launcher
  и JobSpecs для текущего checkout и toolchain. Первые Linux Cargo-команды
  запускать Windows Stillyard Job через проверенный WSL-bootstrap launcher.
  Проверить выбор дистрибутива, окружение, cwd, stdout/stderr, код завершения и
  определённое поведение при cancel/timeout/потере launcher.
- Bootstrap launcher должен контролировать Linux-работу или сохранять явную
  неопределённость, пока её завершение не проверено. Смерть `wsl.exe`/Windows Job
  не принимать за доказательство Linux cleanup. Если этот путь нельзя обеспечить,
  зафиксировать блокирующую причину; прямой Cargo не становится запасным вариантом.

### Каркас протокола, который MR-0 превращает в проверяемый контракт

| Состояние/операция | Право запуска | Обязательство координатора |
|---|---|---|
| Candidate | Нет | Рассматривать готовность, приоритет и полный вектор |
| Offer | Нет | Ограниченно удерживать предложенный вектор; безопасно истекать только неактивированные предложения |
| Arm | После durable подтверждения и местной проверки release | До ответа записать Grant как потенциально используемый; с этого момента не освобождать по TTL |
| Local start / running | Только для связанного Invocation | Сохранять занятость независимо от наличия связи |
| Cleanup / release pending | Нового права запуска нет | Повторять сверку; не считать потерянный ответ доказательством занятости или свободы |
| Released | Нет | Сохранять достаточный tombstone для идемпотентных повторов |
| Uncertain | Нет | Удерживать вектор до доказательства или явного аудированного clearance |

Это не готовая wire-спецификация. MR-0 должна определить линейные точки переходов
и порядок записей на обеих сторонах. В частности:

- Перед Arm местный менеджер сохраняет намерение с идентичностью Grant/Lease.
  Между Arm, местной записью, созданием процесса и release возможен crash;
  восстановление не имеет права запускать Invocation повторно по одному лишь
  отсутствию подтверждения старта.
- Координатор атомарно учитывает весь вектор; местная SQLite атомарно меняет свой
  жизненный цикл. Между ними допускается консервативное удержание, но не
  «общая SQLite-транзакция». Сетевые операции не выполняются под store mutex.
- Offer/reservation и потенциально использованный Grant имеют разные правила
  expiry. Изменение connection epoch отсекает старые сообщения, но не очищает
  работающие процессы и не освобождает их Grant.
- Потерянный release ack исправляется идемпотентным повтором с durable outbox
  либо равноценным протоколом. Отсутствие Grant в произвольном снимке гостя не
  доказывает release: нужны непрерывность истории, согласованный watermark и
  отсутствие ещё не учтённых разрешений/переходов.
- Pairing registry переживает reset SQLite координатора. После потери истории
  затронутые области ресурсов блокируются и для Windows-заданий до сверки всех
  потенциальных владельцев. Неподключившийся участник не считается пустым.
  Потеря самого registry также не разрешает автоматически создать второй authority.
- Для одинакового ресурса версия конфигурации и mapping входят в разрешение.
  Старое разрешение не применяется к новой ёмкости, GPU или иной среде.
- Quiet-release связывает host и local evidence с разрешением, поколениями и
  ограниченной свежестью. Часы разных ОС не сравниваются напрямую. Определяется
  порядок с competing impacts и поведение при suspend/resume или потере связи
  между последней проверкой и release; абсолютный запрет фоновой нагрузки ОС
  не обещается.

### Конкретные артефакты и решения MR-0

Исполнитель создаёт `docs/machine-resource-protocol.md` с нормативным контрактом
и `docs/machine-resource-implementation-status.md` с состоянием работ/evidence,
а также обновляет requirements. Это планируемые файлы, не существующие входные
документы. Протокол должен содержать следующие закрытые решения:

| Решение | Что необходимо записать | Критерий готовности |
|---|---|---|
| Владение состоянием | Таблицы координатора и менеджера, ключи, версии, условия update, GC/tombstones | Для каждого факта есть один авторитет; местный Lease не является вторым независимым распределителем |
| Grant key | Стабильный allocation key для work Lease и отдельного probe Lease; связи с store/Attempt/Invocation | Повтор одной операции совпадает; retry, новый probe и пересозданный store не переиспользуют чужое разрешение |
| Wire API | Запросы/ответы, idempotency key, stale/conflict/unavailable, version negotiation, bounded framing | Потерянный ответ каждого изменяющего запроса имеет однозначный query/retry-путь |
| Порядок запуска | Persist intent, Offer/Arm, подготовка Invocation/Containment, местный commit, фактический release и подтверждение | Crash в любой щели не допускает второго release или признания неизвестной работы пустой |
| Отмена и postconditions | Кто принимает cancel, как останавливается ещё не выпущенный Invocation, как тот же work Grant разрешает postconditions | Cancel не теряется между БД; postcondition не получает права старта после потери актуального допуска |
| Resource accounting | Формулы machine/VM/domain budgets, claims, observations, safety margins и reservations | Численные примеры RAM/CPU/GPU проходят без двойного физического подсчёта и без независимой местной выдачи дефицитного ресурса |
| Fairness | Candidate lifecycle, источник aging, tie-break, clocks, withdrawal и Offer/reservation expiry | Windows и WSL участвуют в одном порядке; stale guest candidate не держит очередь неограниченно |
| Release/reconciliation | Outbox/acks или равноценный durable механизм, полные снимки и watermark, retained uncertainty | Потерянный ack исправляется автоматически; неполный/старый снимок не освобождает активную работу |
| Authority reset | Pairing registry, признак потери истории, restart gate, config epochs, upgrade | После reset не возникает окно выдачи до установки restart gate; потеря registry не создаёт «новую свободную машину» |
| Platform proof | Host/VM/distro/process incarnation, cgroup identity и разрешённые основания ProvenEmpty | Отдельные таблицы для daemon restart, distro terminate, VM shutdown и host reboot; отсутствие данных означает uncertainty |
| Transport и trust | Выбранный локальный мост, направление соединения, pairing, роли, owner/instance authentication и replay fencing | Изолированный тестовый экземпляр или старый мост не могут освобождать Grants настоящей среды |
| Lifecycle среды | Systemd/delegation, установленный executable, reconnect и ограничения keepalive | Автозапуск выполняется без зависимости от интерактивной оболочки; VM lifetime не обещается по одному linger |
| Public API | Scoped accounting, связь Job/Lease/Grant, stale snapshot, blockers, events, doctor/remediation | Пользователь связывает задержку WSL Job с занятым Windows ресурсом через публичные поверхности |
| Совместимость и эксплуатация | SQLite/protocol/schema changes, установка/upgrade, количественный idle budget, пределы сообщений/очередей | Определены downgrade/rejection и безопасная последовательность обновления; нет молчаливого снижения гарантий |
| Bootstrap и consumers | Проверенный Job-launcher, команды W-C1..4, profiles, actual source snapshot, manifest/output locations | MR-3 не зависит от отсутствующей внешней обёртки или невыбранной измерительной команды |

Первый кандидат транспорта — постоянный мост через Windows-режим того же
`stillyard.exe` и owner-only named pipe, с местным Linux IPC. Это предпочтение
для feasibility-проверки, не утверждение его работоспособности. При непригодности
выбрать другой локальный транспорт, сохранить platform-independent протокол и
явно описать изменение требований; не добавлять публичный IP listener скрыто.

Особо проверить bootstrap: обычный Windows runner уже считает закрытие Job
Object доказательством очистки и может освободить Lease при смерти посредника.
Одного обещания WSL-wrapper «ждать ребёнка» недостаточно. Безопасность этого
аварийного пути должна обеспечиваться проверенным механизмом Windows authority
либо иным допустимым путём bootstrap, а не только добросовестным поведением
живой оболочки. До решения не запускать через него Cargo и не засчитывать
Windows containment как Linux evidence.

MR-0 завершается полным контрактом, который можно независимо проверить на
конкретных трассах, а не списком `TODO` по этим строкам. Выбор названий типов,
модулей, сериализации и локальных OS-вызовов делается исполнителем в этих рамках.

**Выход MR-0:** amendment с таблицей отказов и исполнимыми acceptance-сценариями;
выбранный transport/bootstrap; карта текущей поддержки; исходные Windows и WSL
build/check Job ID для одной точно идентифицированной ревизии. Исходный Linux
check может выявить ошибки переносимости: они фиксируются для MR-1/MR-3;
зелёная Linux-сборка не является условием начала её собственного переноса.
Неразрешённые блокеры выбранного пути запуска, authority reset и очистки
не переносятся как неявные допущения.

## MR-1. Общее ядро допуска и платформенные границы

**Цель:** получить проверенную основу на работающей Windows-платформе.

### Работа

- Выделить чистую логику оценки полного вектора и упорядочивания кандидатов из
  `resources.rs`, `store/schedule.rs` и `store/reservation.rs`. Хранилище решений
  координатора и исполнение Windows используют её без дублирующих счётчиков.
- Ввести execution domains и resource identities, иерархические бюджеты и
  отображение `{capacity, granted, reserved}` с областью действия. Локальные
  fences включить в полный вектор как ресурсы соответствующего домена.
- В standalone сохранить атомарный местный путь. Вынести подготовку внешнего
  допуска за пределы транзакции менеджера согласно MR-0.
- Отделить IPC, identity, containment, filesystem и host observation от общих
  lifecycle-функций. Убрать Windows-константы из формирования общих записей,
  восстановления и `doctor`; не копировать весь Windows-runner для Linux.
- Сохранить work Lease на primary/postconditions и отдельные probe Lease.
  Managed-wait проверяет полные claims предков, включая их scoped Grants.
- Добавить транспортно-независимую диагностику: authority, domain, Grant,
  причина ожидания, незавершённая сверка и возраст evidence.

**Проверка:** существующие Windows acceptance по реально поддерживаемым функциям;
полный вектор выдаётся или отклоняется целиком; лимиты машины/VM/контейнера
соблюдаются одновременно; повторное учётное включение предков не увеличивает
физическую заявку. Проверить общий приоритет, aging, reservations, конверсию,
backoff и managed-wait на новом ядре.

**Выход MR-1:** установленная Windows-версия использует новое ядро; результаты
`fmt`, `check`, `test`, `clippy`, MSRV Jobs и сравнение публичного поведения
с базовой ревизией. Это ещё не объявление поддержки WSL.

## MR-2. Durable-протокол подключённой среды

**Цель:** доказать корректность общей выдачи ресурсов до подключения Linux-процессов.

### Работа

- Реализовать протокол MR-0: регистрация, pairing, candidates, Offer/Arm,
  связка с местным Lease/Invocation, release, сверка, повтор сообщений и fencing.
- Подключить к одному координатору Windows-исполнитель и тестовый участник.
  Последний имитирует местные durable переходы и сбои; он не является заменой
  живой WSL-приёмки следующей фазы.
- Реализовать защиту от потери coordinator store, executor store и pairing
  history; version mismatch, изменённой конфигурации, дубликата участника и
  старого соединения. Определить безопасный порядок upgrade/restart.
- Реализовать удалённые кандидаты в общей очереди, конечное удержание Offer,
  withdrawal/deferral и scoped accounting без доменного head-of-line blocking.
- Добавить публичную инспекцию общего бюджета и собственных Grant местного
  задания. При разрыве связи снимок помечается stale/unavailable; нули не
  подставляются. События позволяют восстановить порядок выдач и освобождений.
- Проверить владельца и разрешённую роль peer. Клиент выполнения не может
  выдавать себя за runtime adapter или присылать произвольное доказательство
  очистки другого домена. При этом заявленная модель остаётся cooperative,
  а не защитой от враждебного владельца всей машины.

**Обязательные fault-сценарии:** дублирование, задержка и перестановка сообщений;
потеря ответа Arm и release; crash перед/после каждой durable границы; reconnect
старого и нового экземпляра одновременно; coordinator restart/reset при живом
исполнителе; executor reset при активном Grant; отзыв candidate одновременно
с Arm; отмена и expiry Offer; снижение ёмкости; postconditions и probes.

Для каждого сценария проверяются три свойства: нет двойной выдачи, нет повторного
запуска, а консервативное удержание имеет определённый путь сверки/clearance.
Восстановление после штатного reconnect не должно требовать ручного clear.

**Выход MR-2:** протокол и его отказные сценарии проходят через публичный путь;
Windows продолжает самостоятельно исполнять реальные Jobs. Аварийные проверки
выполняются внутри изолированных экземпляров, запущенных системным Job.

## MR-3. WSL2 вместе с Windows — большая фаза с живыми потребителями

**Цель:** установить рабочую пару демонов на текущей машине. Windows и WSL
динамически делят ресурсы через один координатор. Эта фаза не завершается
компиляцией Linux-бинарника, smoke-тестом или статическим разделением слотов.

### MR-3.1. Linux-исполнитель и местный менеджер

- Unix-сокет владельца, peer identity, singleton store/endpoint, default autostart,
  connect-only явные endpoints и изолированные экземпляры.
- Путь запуска в делегированном cgroup v2 с born-contained процессом и барьером
  до пользовательского кода. PID identity/pidfd, идентичность фактически
  запускаемого executable и shebang, стабильность рабочего каталога.
- stdin, canonical stdout/stderr, timeout/cancel, cleanup потомков, uncertain,
  probes/postconditions, retries и предзапусковые повторные проверки.
- Linux-файловые identities, fences, чистое окружение, atomic file publication
  и flush. Для первой установки store находится на проверенной локальной ФС
  внутри WSL; shared Windows paths получают отдельные явно поддержанные правила.
- WSL-инкарнация дистрибутива, VM и процесса демона. Различить logout, daemon
  crash, terminate дистрибутива, shutdown VM и reboot Windows. Проверить
  сохранность cgroup-доказательств после каждого события.
- Проверить WSL interop как границу containment. Не заявлять очистку Windows
  потомков по одному Linux cgroup. Поддержанный режим и ограничения фиксируются
  в `doctor` и исполнимых отрицательных сценариях.

### MR-3.2. Подключение к Windows-координатору

- Реализовать выбранный MR-0 локальный мост и явное связывание установленного
  WSL-демона с системным Windows-координатором. Мост передаёт протокол, но его
  exit не служит доказательством очистки Linux.
- Windows-задания и WSL-задания участвуют в одной очереди допуска, включая
  машинные `cargo_slots`, CPU/RAM бюджеты, custom tokens и impacts. Для WSL
  учитываются также фактические ограничения VM/дистрибутива.
- Подключить host и guest observation. Отдельно определить корректный дебет
  RAM, влияние vmmem, provenance и свежесть CPU/disk/process evidence.
  CPU/impact quiet-сценарий включён в приёмку; его нельзя заменить постоянным
  unsupported. GPU/NVML принимается отдельно при наличии подходящего устройства;
  иначе публикуется точная ограниченная capability, без заявления GPU-паритета.
- Провести реальные coordinator/WSL disconnect и restart. Показать, что общий
  бюджет остаётся занят активными/uncertain заданиями и автоматически сверяется
  после штатного восстановления связи.

### MR-3.3. Установка и собственные сборки

- Установить Linux CLI/daemon по постоянному пути вне Cargo target; выбрать
  поддержанный запуск под user manager и проверить делегирование/lifetime.
  VM keepalive и logout описываются отдельно. Открытый клиент не считается
  гарантией жизни VM.
- Добавить Linux-launcher и JobSpecs для `fmt`, `fmt-write`, `check`, `test`,
  `clippy`, `msrv-check`, `msrv-test`, `schema-update`, `build-release`.
  MSRV остаётся 1.85; окружение явное; Cargo target отдельный.
- Перевести WSL-валидацию с bootstrap на установленный системный WSL-демон,
  прикреплённый к Windows-координатору. Обновить AGENTS.md и CONTRIBUTING.md,
  сохранив обязательное исполнение Cargo через системный Stillyard Job.
- Проверить upgrade обеих сторон, недопустимую версию peer, недоступный хост,
  восстановление клиента и диагностику. Снять Windows-регрессию на той же
  ревизии, что установлена в WSL; не смешивать результаты разных checkout.

### MR-3.4. Живые потребители

Потребительские сценарии берутся из существующего
[review-fleet case](consumer-case-review-fleet.md) и собственного development
workflow. Устаревшие illustrative JobSpec из case переписываются под действующую
схему; отсутствие готового `fleet` binary не скрывается. При необходимости
используется тонкий адаптер существующих CLI, а не новая агентская оркестрация.

| ID | Потребитель и реальная работа | Что доказывает |
|---|---|---|
| W-C1 | Нативные Windows и WSL сборки/тесты Stillyard одной ревизии | Общий `cargo_slots`: при 1 старты сериализованы между ОС; при 2 совместимые Jobs перекрываются |
| W-C2 | Реальный раунд доступных Claude/Grok/Codex CLI над конкретным brief/diff, с проверкой выходного verdict | Длительные Jobs переживают потерю клиента; canonical logs, typed result и postconditions работают; собственно ревью не монополизирует слот сборки |
| W-C3 | Агент-потребитель в WSL запрашивает реальный managed build/test в scratch worktree, пока идёт Windows-сборка | Самостоятельный допуск ребёнка, безопасный wait, idempotency/recovery и общий машинный токен без ancestor deadlock |
| W-C4 | Реальная измерительная команда выбранного проекта конкурирует с Windows/WSL сборкой | `measurement` против `cpu_heavy` и свежая quiet-проверка действуют между ОС; команда, метрика и критерий результата фиксируются до прогона |

Для W-C2 фиксируются фактическая модель, профиль и subscription/provider route;
синтетический JSON не заменяет ответ живого CLI. Для W-C3 нельзя заставлять
агента вызывать Cargo напрямую: сборку создаёт управляемый consumer adapter.
Если внешний измерительный проект недоступен, до W-C4 выбирается реальная
воспроизводимая команда в доступном checkout и заранее определяется её результат.

Каждый сценарий оставляет manifest: revision, версии двух установленных демонов,
host/domain/store identities, спецификации и хеши конфигурации, Job/Attempt/Grant
ID, canonical logs/events, результаты и containment evidence. Общность слота
доказывается порядком выдач/освобождений и стартов, а не редкими снимками загрузки.

### MR-3.5. Матрица приёмки и критерий завершения

- W-C1..4 проходят на текущей машине. Повторяются не менее трёх потребительских
  раундов; один включает потерю клиента и reconnect, другой — рестарт демона
  между раундами. Сбои во время работы проверяются отдельно от успешных раундов.
- Активная WSL-сборка удерживает общий токен при потере моста. Windows-сборка
  не стартует поверх неё. Восстановление исправляет потерянный release ack.
- Fault-harness воспроизводит restart/reset coordinator store при живом Linux
  процессе, а также reset местного store. Новая пустая БД не означает свободную
  машину. Эти разрушительные случаи проверяются на изолированных экземплярах
  внутри системного Job, без сброса пользовательских очередей.
- Прогоны, останавливающие WSL VM целиком, управляются Windows-системным Job и
  внешним harness: WSL-демон под проверкой не планирует собственное исчезновение.
  Перед таким прогоном проверяется отсутствие посторонней работы в затронутых
  дистрибутивах; неустранимое влияние на неё требует отдельного согласования.
- Timeout/cancel, root exit с живыми потомками и forced cleanup failure дают
  правильные результаты и retained Lease/Grant. Повтор ключа не создаёт новую работу.
- Остановка/возобновление VM, terminate дистрибутива и logout имеют наблюдённые
  результаты, записанную границу гарантий и путь восстановления. Нарушение
  внешнего keepalive не маскируется успешным тестом закрытия одного терминала.
- Проверены общий priority/aging, несовместимые impacts, нет доменного
  head-of-line blocking и нет ложного успеха за счёт полной сериализации всей работы.
- Установленные default-демоны обслуживают повседневный путь сборки. Windows
  и WSL gates зелёные, включая MSRV. Измерены idle CPU/memory/wakeups с учётом
  моста; новые нормы были определены в MR-0 относительно A-19.
- README, CLI help, doctor и consumer adapters описывают реально доступные
  операции. Неподдержанные GPU/runtime capabilities перечислены отдельно.

**Выход MR-3:** используемый Windows/WSL продукт, report с Job ID и реальными
потребительскими результатами, воспроизводимые launchers и проверенная процедура
обновления. Контейнеры и native Linux не задерживают этот выпуск.

## MR-4. Standalone Linux и dev-контейнеры на Linux/WSL

**Цель:** проверить обобщение на несколько сред, не вводя новый алгоритм допуска.

### Работа

- На отдельном native Linux-хосте установить тот же демон с местным координатором.
  Собрать независимые Linux acceptance-результаты: WSL evidence их не заменяет.
- Подключить один выбранный контейнерный runtime сначала с двумя, затем с десятью
  заранее созданными dev-контейнерами. Повторить на WSL под Windows authority.
- Реализовать ограниченный runtime adapter: идентичность и incarnation контейнера,
  регистрация домена/лимитов, каналы к исполнителю и доказательства удаления.
  Проверить делегированное cgroup; неподдержанный rootless/permission режим
  диагностируется, а не заменяется process-group-only cleanup.
- Определить расположение durable местного store/logs: постоянный том либо
  менеджер вне одноразового контейнера. Пересоздание среды, clone тома и старое
  имя не позволяют присвоить чужие полномочия или стереть active Grant.
- Добавить явный mapping общих bind mounts/cache и ресурсных identities.
  Проверить одинаковые пути к разным каталогам и разные пути к одному каталогу.
- Проверить иерархические CPU/RAM ограничения, общий слот и impacts, фоновые
  процессы контейнера, stale evidence и справедливость между активными средами.
- На удалённом Linux-хосте повторить consumer-путь: его контейнеры получают
  ресурсы от его координатора; клиент на ноутбуке не влияет на выбор authority.

**Приёмка:** десять контейнеров с реальными build/test Jobs при двух общих слотах;
использование свободного бюджета активными контейнерами без изменения квот;
managed build внутри контейнера; удаление/пересоздание занятой среды; потеря
runtime adapter; конфликт с нативным host Job. Отдельно проверяется VM-лимит
при двух контейнерах, каждый из которых по отдельности помещается в свой лимит.

**Выход MR-4:** поддержанный runtime/profile для Linux и WSL, native Linux report,
consumer manifests и capability matrix. Оркестратор создаёт среду; Stillyard
координирует работу после её явного подключения.

## MR-5. macOS и dev-контейнеры

**Цель:** перенести машинный координатор и observation на Mac, сохранив Linux
исполнение внутри поддержанного контейнерного runtime.

### Работа

- Выбрать один runtime и Mac-стенд; зарегистрировать фактическую VM/container
  топологию. Не предполагать одну общую VM для всех возможных продуктов.
- Реализовать host identity, lifecycle координатора, local IPC/bridge и
  CPU/RAM/process/disk observation на macOS; подключить существующий Linux executor.
- Определить доступность GPU и host-wide quiet по фактическому provider coverage.
  NVIDIA UUID/NVML не объявляются универсальной моделью всех Mac GPU.
- Проверить sleep/wake хоста, VM restart, контейнерные reincarnation и потерю
  связи с теми же правилами удержания Grant и fencing.
- Повторить MR-4 с живыми dev-контейнерными потребителями и наблюдаемой фоновой
  macOS-нагрузкой. Доказать использование неизменённого алгоритма допуска и
  основных протокольных acceptance-сценариев.

**Выход MR-5:** Mac координирует контейнерную работу и учитывает доступную
host evidence. Запуск произвольных нативных macOS Jobs с гарантией полного
containment — отдельная поставка, если понадобится; эта фаза её не подразумевает.

## Единые правила реализации и evidence

- Каждый implementation-срез указывает фазу, затронутые требования и исполнимый
  сценарий. Для safety-инварианта нужен отрицательный контроль, который обнаружит
  двойную выдачу, преждевременный release или повтор пользовательского запуска.
- Каждый Cargo build/check/test/Clippy/rustfmt/MSRV/schema invocation на этом
  хосте выполняется через default Stillyard Job согласно [AGENTS.md](../AGENTS.md).
  В отчётах обязательны Job ID и ревизия; прямые Cargo-результаты не принимаются.
- Изолированные демоны служат объектами тестов; планирующим их Job остаётся
  системный default daemon. Тесты чужих аварий не останавливают его ресурсный учёт.
- Fault-тесты отделены от live-consumer evidence. Simulator не доказывает Linux
  containment, пустой сценарий не доказывает общую очередь, WSL не доказывает Mac.
- Перед закрытием MR-2 проверяется протокол и карта отказов; перед MR-3 — код,
  реальные результаты и восстановление. Независимые ревью оцениваются по
  воспроизводимым находкам; неподтверждённое предположение не становится контрактом.
- На каждой границе фазы обновляется короткий status/evidence ledger: что
  поставлено, какие ограничения наблюдены, ссылки на Jobs и следующий срез.
  Фаза закрывается по результату, а не по числу созданных модулей.

### Минимальная матрица отрицательных контролей

Эти ID используются в status ledger и будущих tests/reports. MR-2 проверяет
протокол на тестовых участниках, MR-3 повторяет связанные случаи с реальным
Linux cleanup; от одного mock-прогона обе колонки не становятся завершёнными.

| ID | Сценарий | Ошибка, которую проверка обязана обнаружить | Фаза |
|---|---|---|---|
| M-A01 | Windows и WSL одновременно просят единственный machine token | Независимая выдача в двух доменах | MR-2, MR-3 / W-C1 |
| M-A02 | Два разрешённых слота, две совместимые реальные работы | Реализация «один глобальный mutex на всё» вместо векторного планировщика | MR-2, MR-3 / W-C1 |
| M-A03 | Высокоприоритетный заблокированный кандидат и совместимая работа другого домена | Head-of-line blocking или скрытие всех кандидатов за одним доменным head | MR-2, MR-3 |
| M-A04 | Crash/дублирование до и после Arm, local commit и release | Второй пользовательский запуск или TTL-release потенциально использованного Grant | MR-2, MR-3 |
| M-A05 | Потеря моста/ack при живой работе и после её очистки | Heartbeat-as-empty или постоянная утечка токена после штатной сверки | MR-2, MR-3 |
| M-A06 | Coordinator reset, guest reset, утрата/повреждение pairing history | Новая пустая база немедленно объявляет ресурсы свободными | MR-2, MR-3 |
| M-A07 | Старый peer и новый peer предъявляют один domain; reuse имени контейнера | Чужая очистка/повторное использование старого Grant | MR-2, MR-3, MR-4 |
| M-A08 | Cancel и root exit при живом потомке, cleanup failure | Root-only kill или освобождение Grant до доказательства пустоты | MR-3 |
| M-A09 | Primary, postconditions и probe | Grant ошибочно освобождён между primary и postconditions либо probe использует чужой work Lease | MR-2, MR-3 |
| M-A10 | Родитель ждёт реальную дочернюю сборку при общих scoped claims | Пропуск ancestor conflict или двойная выдача при replay ensure | MR-3 / W-C3 |
| M-A11 | Межсредовые impacts, stale quiet evidence, suspend/resume | Измерение стартует при конфликтующей управляемой работе или по просроченному sample | MR-2, MR-3 / W-C4 |
| M-A12 | Host reboot, VM shutdown, distro terminate и daemon restart | Любая смена generation ошибочно считается смертью всех процессов | MR-3, MR-4, MR-5 |
| M-A13 | Machine/VM/container budgets и физический GPU с aliases | Превышение ограничения предка или создание второй копии физического ресурса | MR-1, MR-4 |
| M-A14 | Shared directory под разными путями и разные каталоги под одним путём | Обход общего fence или ложное объединение независимых каталогов | MR-4 |

Проверки, которые отключены из-за отсутствующей capability, записываются как
не выполненные с конкретной причиной. Они не превращаются в pass. Для обязательных
строк текущей фазы отсутствие среды означает незавершённую приёмку.

### Состояние передачи и формат ledger

Начальное состояние: MR-0..MR-5 — `not_started`; M-A01..14 и W-C1..4 — `not_run`.
Этот документ не является evidence их прохождения. Создаваемый в MR-0 status
ledger должен содержать:

| Поле | Содержимое |
|---|---|
| Текущий срез | Фаза, конкретный результат, `not_started / in_progress / blocked / complete` |
| Source identity | Commit и, если есть, хеш незакоммиченного diff; platform/toolchain |
| Контракт | Какие MR-0 решения закрыты, какие requirements amended, оставшиеся вопросы |
| Изменения | Модули и пользовательское поведение; установленные версии отдельно от target build |
| Проверка | M-A/W-C ID, actual Stillyard Job ID, исход и ссылки на canonical evidence |
| Ограничения | Подтверждённая capability, неизвестное, внешний blocker; без подмены skip на pass |
| Следующее действие | Конкретная операция, которую можно выполнить без пересказа прошлой сессии |

Начальный implementation-срез — обследование/bootstrap и контракт MR-0.
Не начинать с переписывания runner целиком или добавления no-op провайдеров,
которые позволят назвать Linux поддержанным. Технические stubs при выделении
платформ допустимы только с явным unsupported и не закрывают runtime acceptance.

  требуют классического 2PC, что отсутствие строки в `wsl --list --running`
  доказывает очистку, или что отсутствие `WSL_INTEROP` гарантированно блокирует
  любой выход из Linux containment. Предложение получать scarce leases
  последовательно у нескольких планировщиков заменено единым полным вектором
  координатора. Предложение освобождать Grant по отсутствию в любом guest snapshot
  заменено требованием durable reconciliation с непрерывной историей.
  Эти выводы уже включены в план; повторять прежнее ревью для восстановления
  контекста не требуется. Исторический Fable запуск через
  `claude2 -p --model fable --effort xhigh` разрешился в `claude-fable-5-1`, а не в ожидавшийся старым skill
  `claude-fable-5`; новые consumer validators проверяют фактический modelUsage.
